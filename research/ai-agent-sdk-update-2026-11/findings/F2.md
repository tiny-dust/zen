# F2：官方 Agent 实践、SDK 与 MCP（子问题 3、4）

## 结论

**应优先借鉴机制，不应仅为这些能力迁移 Agent 框架。** 最适合本地编码桌面 Agent 的候选是：按风险分层的可恢复审批、默认不外传内容的运行轨迹、稳定核心工具加按需发现、可重读结果清理加结构化压缩。多 Agent 优先保持主 Agent 汇总、子 Agent 返回结果，不默认把整个用户会话转交给子 Agent。

本文件没有检查 Zen 源码；下文均是**待 F3 对照的设计候选，不是 Zen 缺失清单**。不建议根据本文件直接修改产品、升级依赖或启用远程遥测。

## 候选实施顺序（需与 F3 源码结果合并）

| 顺序 | 候选 | 原因 | 前置条件 |
|---|---|---|---|
| P0 | 审批/恢复不变量测试＋本地脱敏轨迹 | 先防误执行和数据外泄，再优化成本；可独立于框架完成。 | 确认已有审批、事件、持久化和取消链路，避免重复实现。 |
| P1 | 稳定工具目录＋按需发现试验 | 多 MCP/大工具集更可能获益；小工具集不必增加搜索。 | 量化工具定义 token 和误选率；保留全量模式回退。 |
| P1 | 可重读结果清理＋结构化压缩质量评估 | 分别降低结果膨胀和长会话增长，优先解决真实瓶颈。 | 具备摘要前后约束对比、历史结果引用和不可清除类别。 |
| P2 | 多 Agent 上下文过滤与权限收窄 | 通常比新增 Agent 数量更能控制风险与总成本。 | 已有子任务调度和宿主资源锁；先单 Agent 基线。 |
| P3 | 模型生成程序编排工具 | 潜在高收益但新增执行面最大，不适合作为首批默认能力。 | 沙箱、最小权限代理、逐项审批、可取消与可审计均通过测试。 |
