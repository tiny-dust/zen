# F5: 框架与 API 原生能力的上下文管理

## Findings

### [1] Anthropic 的 context editing beta 提供两种服务端清理策略：`clear_tool_uses_20250919`（工具结果清理，参数 trigger/keep/clear_at_least/exclude_tools）与 `clear_thinking_20251015`（thinking 块清理，keep 最近 N 轮或 "all"），清理在 API 服务端进行、客户端保留完整历史，启用需 beta header `context-management-2025-06-27`
- quote: "The `clear_tool_uses_20250919` strategy clears tool results when conversation context grows beyond your configured threshold. ... The API replaces each cleared result with placeholder text indicating to Claude that it was removed. ... Context editing is applied server-side before the prompt reaches Claude. Your client application maintains the full, unmodified conversation history."
- url: https://docs.anthropic.com/en/docs/build-with-claude/context-editing
- source_type: primary
- published: unknown (beta header context-management-2025-06-27; feature announced 2025-09-29)
- confidence: high
- 细节：trigger 示例为 `{"type": "input_tokens", "value": 30000}`，keep 示例为 `{"type": "tool_uses", "value": 3}`，clear_at_least 示例为 `{"type": "input_tokens", "value": 5000}`；`clear_tool_inputs: true` 可连 tool call 参数一起清；`exclude_tools` 可豁免指定工具；多个策略并用时 `clear_thinking_20251015` 必须排在 edits 数组首位。

### [2] Anthropic 明确指出工具结果清理会使 prompt cache 前缀失效、每次清理都产生 cache write 成本，因此建议用 `clear_at_least` 保证每次至少清理足够 token 让缓存失效"值得"
- quote: "Tool result clearing: Invalidates cached prompt prefixes when content is cleared. To account for this, clear enough tokens to make the cache invalidation worthwhile. Use the `clear_at_least` parameter to ensure a minimum number of tokens is cleared each time. You'll incur cache write costs each time content is cleared, but subsequent requests can reuse the newly cached prefix."
- url: https://docs.anthropic.com/en/docs/build-with-claude/context-editing
- source_type: primary
- published: unknown
- confidence: high

### [3] Anthropic 官方宣称（2025-09-29 发布）：在内测 agentic search 评测中，memory tool + context editing 组合比基线提升 39%，context editing 单独提升 29%；在 100 轮 web search 评测中 context editing 让原本会因上下文耗尽而失败的任务得以完成、同时减少 84% token 消耗
- quote: "combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement. In a 100-turn web search evaluation, context editing enabled agents to complete workflows that would otherwise fail due to context exhaustion—while reducing token consumption by 84%."
- url: https://www.anthropic.com/news/context-management
- source_type: primary
- published: 2025-09-29
- confidence: high (数字为厂商自报内部评测)

### [4] OpenAI Responses API 仍保留 `truncation` 参数：默认 `disabled`（输入超窗直接 400 报错——正是 Zen 遇到的溢出故障模式），设为 `auto` 则由模型从会话开头丢弃 item 以适配窗口
- quote: "auto: If the input to this Response exceeds the model's context window size, the model will truncate the response to fit the context window by dropping items from the beginning of the conversation. disabled (default): If the input size will exceed the context window size for a model, the request will fail with a 400 error."
- url: https://developers.openai.com/api/reference/resources/responses/methods/create.md
- source_type: primary
- published: unknown (live API reference)
- confidence: high

### [5] OpenAI 已将长会话管理的主推方案升级为"服务端 compaction"：`/responses` 请求加 `context_management: [{type: "compaction", compact_threshold}]`（示例 200,000 token）自动触发压缩并流式返回不透明的加密 compaction item；另有独立 `/responses/compact` 端点做显式无状态压缩，返回的窗口应原样传给下一次调用
- quote: "When the rendered token count crosses the configured threshold, the server runs server-side compaction. ... The returned compaction item carries forward key prior state and reasoning into the next run using fewer tokens. It is opaque and not intended to be human-interpretable. ... You send a full context window (messages, tools, and other items), and the endpoint returns a new compacted context window you can pass to your next `/responses` call as-is."
- url: https://developers.openai.com/api/docs/guides/compaction
- source_type: primary
- published: unknown (live docs; API reference confirms `context_management` 目前仅支持 "compaction" 类型)
- confidence: high
- 细节：`store=false` 时服务端 compaction 兼容 ZDR；官方 latency tip：stateless 链式调用可在追加输出后丢弃最近 compaction item 之前的旧 item，但用 `previous_response_id` 链式调用时不要手动裁剪。

### [6] OpenAI 明确提示：即使用 `previous_response_id` 链式会话，链上所有历史输入 token 仍按 input token 计费——服务端持有状态不等于节省成本，压缩才是降本手段
- quote: "Even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API."
- url: https://developers.openai.com/api/docs/guides/conversation-state
- source_type: primary
- published: unknown (live docs)
- confidence: high

### [7] LangChain 内置 `SummarizationMiddleware`：配置一个单独的摘要模型、token 触发阈值和保留条数即可实现"历史超限时摘要替换"，示例为 trigger=("tokens", 4000) + keep=("messages", 20)，与 trim/delete 并列为三大短期记忆策略
- quote: "To summarize message history in an agent, use the built-in [`SummarizationMiddleware`] ... SummarizationMiddleware(model=\"gpt-5.4-mini\", trigger=(\"tokens\", 4000), keep=(\"messages\", 20))"
- url: https://docs.langchain.com/oss/python/langchain/short-term-memory
- source_type: primary
- published: unknown (live docs)
- confidence: high
- 细节：trim 通过 `@before_model` 中间件 + `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 实现；文档同时给出 trim / delete / summarize 三条路径。

### [8] LangChain 文档特别警告：删消息时必须保持消息序列对 provider 合法——历史通常要以 user 消息开头、assistant 的 tool call 必须紧跟对应 tool 结果，这是任何截断实现都要遵守的完整性约束
- quote: "When deleting messages, **make sure** that the resulting message history is valid. Check the limitations of the LLM provider you're using. For example: Some providers expect message history to start with a `user` message; Most providers require `assistant` messages with tool calls to be followed by corresponding `tool` result messages."
- url: https://docs.langchain.com/oss/python/langchain/short-term-memory
- source_type: primary
- published: unknown (live docs)
- confidence: high

### [9] Vercel AI SDK 的 agent 循环通过 `prepareStep` 做步间上下文管理：回调返回的 `messages` 覆盖会持久化为后续步骤的消息基线，官方示例在估算 token 超过阈值（示例 100,000）时调用内置 `pruneMessages`（`reasoning: 'all'`, `toolCalls: 'before-last-3-messages'`, `emptyMessages: 'remove'`）实现压缩
- quote: "Long-running agents can accumulate large tool results, reasoning parts, and assistant messages. Use `prepareStep` to mutate the message state that will be used by later steps. This is useful for compaction, and you decide when compaction should happen."
- url: https://ai-sdk.dev/docs/agents/loop-control
- source_type: primary
- published: unknown (live docs)
- confidence: high
- 细节：官方示例的 token 估算用 `JSON.stringify(messages).length / 4`；同页还支持每步换模型、每步 `activeTools`/`toolChoice`；`stopWhen` 默认 20 步上限。

### [10] LlamaIndex 两代记忆模块均为 token 阈值驱动的自动裁剪：旧版 `ChatMemoryBuffer`（现已标注 deprecated）默认 token_limit=3000 或取模型 context_window×0.75，超限丢最旧消息但保持 tool/assistant 配对；新版 `Memory` 默认 token_limit=30000、chat_history_token_ratio=0.7，FIFO 超限时按 flush 批量（默认 limit×10%）弹出最旧消息"waterfall"进 memory blocks 并保证按完整对话轮次弹出
- quote: "DEFAULT_TOKEN_LIMIT_RATIO = 0.75; DEFAULT_TOKEN_LIMIT = 3000 ... Deprecated: Please use `llama_index.core.memory.Memory` instead." / "When the FIFO queue reaches the token limit, the oldest messages within the pressure size are ejected from the FIFO queue. The messages are then processed by each memory block."
- url: https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/memory/chat_memory_buffer.py （Memory: https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/memory/memory.py）
- source_type: primary
- published: unknown (main branch source)
- confidence: high
- 细节：新版 memory block 有 priority 字段（0=永不截断），block 内容注入 system 消息或最新 user 消息。

### [11] Letta 在会话历史超出 context window 时自动触发 compaction（摘要），`compaction_settings` 提供四种模式：默认 `sliding_window`（sliding_window_percentage=0.3，即摘要最旧 ~30% 保留 ~70%，仍放不下时按 ~10% 步进加大摘要比例）、`all`、以及为 prompt cache 优化的 `self_compact_sliding_window`/`self_compact_all`；摘要上限 50,000 字符，默认摘要模型按 provider 取 claude-haiku-4-5 / gpt-5-mini / gemini-2.5-flash
- quote: "When an agent's conversation history grows too long to fit in its context window, Letta automatically **compacts** (summarizes) older messages to make room for new ones. ... `sliding_window_percentage=0.3` (summarizes ~30% of messages and keeps ~70%; increases the summarized portion in ~10% steps if needed to fit the token budget) ... Self-compaction modes keep the agent's system prompt and tools in the summarization request. This means the LLM provider can serve the request from its prompt cache, since the prefix matches normal agent requests."
- url: https://docs.letta.com/v1-sdk/messages/compaction/
- source_type: primary
- published: unknown (live docs; V1 SDK 标注为 legacy)
- confidence: high

### [12] Letta 的分层记忆把"该记什么"按规模/重要性分四层并给出具体配额：memory blocks（可被 agent 用 memory_rethink/memory_replace/memory_insert 工具自我编辑，单 agent 建议 <20 个、总计 <50k 字符）、Files（只读、可 open/close/搜索，5MB，建议 <100 个）、Archival Memory（读写向量库）、External RAG（无限规模、走自定义工具/MCP）
- quote: "For smaller amounts of data, it is best to simply place everything into the context window with memory blocks. For larger amounts of data, you may need to store data externally and retrieve it." （表格：Memory Blocks — Recommended <50k characters, Recommended <20 blocks per agent; Files — 5MB, Recommended <100 files per agent）
- url: https://docs.letta.com/v1-sdk/memory/context-hierarchy/
- source_type: primary
- published: unknown (live docs)
- confidence: high
