# F6: 上下文压缩的工程最佳实践与失败模式

调研日期：2026-10-12。方法：DuckDuckGo/Bing 搜索被 CAPTCHA/垃圾结果阻断后，改用已知一手来源直取 + HN Algolia / GitHub Issues API 检索。所有引用页面均已实际抓取。

## Findings

### [1] Anthropic 官方将 compaction 定义为"接近窗口上限时总结对话并以摘要重启"，Claude Code 的实现保留架构决策、未解决 bug 与实现细节，丢弃冗余工具输出，用"压缩上下文 + 最近访问的 5 个文件"继续会话
- quote: "The model preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs or messages. The agent can then continue with this compressed context plus the five most recently accessed files."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: primary
- published: 2025-09-29
- confidence: high

### [2] Claude Code 官方文档给出了结构化摘要的固定内容类别（用户请求与意图、关键技术概念、已查看/修改文件及重要代码片段、错误及修复、待办任务、当前工作），明确"完整工具输出与中间推理不保留"，压缩后自动重读最近修改的最多 5 个文件并重注入已调用过的 skill 内容（skill 描述列表不重注入）
- quote: "The summary keeps: your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work. It replaces the verbatim conversation: full tool outputs and intermediate reasoning are gone."
- url: https://code.claude.com/docs/en/context-window
- source_type: primary
- published: unknown
- confidence: high

### [3] Anthropic 对压缩 prompt 的调优方法论是"先最大化召回、再迭代提精度"，并把"工具结果清除"（tool result clearing，已作为 Claude 平台 context management 特性发布）列为最安全、最轻量的第一级压缩手段
- quote: "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information from the trace, then iterate to improve precision by eliminating superfluous content."
- url: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- source_type: primary
- published: 2025-09-29
- confidence: high

### [4] Anthropic prompt cache 按断点处的前缀哈希缓存——"断点前任何 block 变化都会改变哈希"，回看窗口仅 20 blocks、写入只发生在断点；因此任何改写消息历史的 compaction（把摘要替换进历史）必然使整条会话缓存失效、下一轮全量重算，这是"压缩时机 vs 前缀缓存"冲突的机制根源
- quote: "Because the hash is cumulative, covering everything up to and including the breakpoint, changing any block at or before the breakpoint produces a different hash on the next request."
- url: https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- source_type: primary
- published: unknown
- confidence: high

### [5] 缓存 TTL 与定价让压缩时机有真实成本：默认 5 分钟 TTL 从请求开始计时且生成时间计入（流式响应花 4 分钟则后续请求只剩约 1 分钟命中窗口）、每次命中免费续期；1 小时 TTL 写入价为基准 2 倍、5 分钟写入 1.25 倍、命中读取约 0.1 倍——压缩后的第一轮请求等于全价 cache write
- quote: "The lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response. Time spent generating a response counts against the lifetime."
- url: https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- source_type: primary
- published: unknown
- confidence: high

### [6] Claude Code 的官方阈值体系是"窗口大小 × 百分比"两级参数：CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 设定触发百分比（1–100，只能调低、高于默认值被忽略，主会话与 subagent 都生效）；CLAUDE_CODE_AUTO_COMPACT_WINDOW 可设 100k–1M tokens 且被模型上下文上限截断；原生 1M 模型默认约 967K tokens（≈96.7%）触发，未识别模型 ID 与无扩展上下文的模型按 200K 边界压缩
- quote: "Set the percentage (1-100) of the auto-compact window at which auto-compaction triggers. Use lower values like `50` to compact earlier; the variable can't raise the threshold, so values above the default percentage are ignored."
- url: https://code.claude.com/docs/en/env-vars （阈值细节另见 https://code.claude.com/docs/en/model-config#default-auto-compact-thresholds ）
- source_type: primary
- published: unknown
- confidence: high

### [7] Claude Code 的超限兜底依赖"API 报错文案可识别"，并有独立的压缩失败终态：对不认识的模型 ID 可配置为仅在 API 返回可识别 too-long 错误后才压缩恢复，"网关改写错误文案后该恢复不运行"；错误参考中单列"Prompt is too long · automatic compaction failed:"与"A single-exchange conversation cannot be compacted"；fallback 模型链明确拒绝换到更小窗口的模型做压缩（否则摘要点会截断对话）
- quote: "Claude Code doesn't run that recovery when a gateway rewrites the error to wording Claude Code doesn't recognize."
- url: https://code.claude.com/docs/en/model-config （错误终态见 https://code.claude.com/docs/en/errors#prompt-is-too-long ）
- source_type: primary
- published: unknown
- confidence: high

### [8] Claude Code 团队成员（Boris Cherny）公开确认缓存与窗口的现实冲突：主 agent 用 1 小时 cache window，闲置 1 小时后继续会话常是全量 cache miss，官方因此调查把上下文默认改为 400k（提供 CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000 实验）
- quote: "Since Claude Code uses a 1 hour prompt cache window for the main agent, if you leave your computer for over an hour then continue a stale session, it's often a full cache miss."
- url: https://news.ycombinator.com/item?id=47740541 （HN 讨论 "Pro Max 5x quota exhausted in 1.5 hours despite moderate usage"，2026-04-12）
- source_type: community
- published: 2026-04-12
- confidence: high

### [9] Cline 的超限检测与自动恢复设计（PR #12804，2026-08-03 合并）：在 provider 错误分类层识别 context_window_exceeded（带 429/限流措辞否决——"TPM-limit messages also say 'tokens exceeded'"），恢复时绕过 token 估算触发器、强制走确定性"basic"压缩而非 LLM 摘要器（"the agentic summarizer call budgets with the same estimator that undercounted, so it could overflow too"），每次 run 只重试一次；"单条超大首 prompt"直接失败且不重发注定失败的请求，并把原始 provider 报错附在提示后（"prompt is too long: 213462 tokens > 200000 maximum"）
- quote: "on a classified overflow, force a compaction through `prepareTurn` and retry the request. The user sees a status notice (\"context window exceeded — compacting and retrying\"), not an error."
- url: https://github.com/cline/cline/pull/12804
- source_type: primary
- published: 2026-08-03
- confidence: high

### [10] Cline 收紧了自动压缩的前置条件（PR #14867，2026-10-06）：未知自定义模型曾继承猜测的 128k 输入预算，大启动 prompt 误触发"无历史可压缩"的自动压缩并显示"Compaction skipped"；修复后自动压缩要求已知/已配置的输入上限，手动压缩与"provider 确认的超限恢复"仍用默认预算保留
- quote: "Require a known or configured input limit for automatic compaction. Keep manual compaction and provider-confirmed overflow recovery available with the default working budget."
- url: https://github.com/cline/cline/pull/14867
- source_type: primary
- published: 2026-10-06
- confidence: high

### [11] Cline 社区 issue 记录的失败模式清单：硬编码 300KB 文件读取上限 + "prompt too long" 无恢复、用户只能弃任务重来（#4389）；"Input too long" 重试死循环、只能手动回滚 checkpoint，建议自动丢弃最新上下文并注入说明"(Truncated due to context window limits.)"（#5251）；本地计数与 provider 实际不符——"400 number of input tokens (189413) have exceeded max prompt tokens (163840) limit"（#6055）；反复手动压缩后 token 统计异常 200K→60K→18K（#12996）；模型元数据错误导致不压缩直接超限、需手动换模型恢复（#12111）
- quote: "Retries won't help since the context window isn't automatically shrinking, you'll just hit the same error again. The only way out is to manually roll back to an earlier checkpoint."
- url: https://github.com/cline/cline/issues/5251 （另见 /issues/4389 、/issues/6055 、/issues/12996 、/issues/12111 ）
- source_type: community
- published: 2025-07-30
- confidence: medium

### [12] Claude Code 用"默认硬上限 + 落盘重读"治理工具输出：bash 输出默认 30000 字符（上限 150000）；后台任务输出从 v2.1.277 起写入文件、由 Read 工具按需读取（TASK_MAX_OUTPUT_LENGTH 废弃）；hook 输出超 10000 字符自动存文件、只给 Claude 预览 + 文件路径；skill 元数据字符预算按上下文窗口 1% 动态计算（回退 8000 字符）
- quote: "Maximum number of characters of bash output that Claude Code reads back into a command's result (default: 30000; maximum: 150000)." （落盘模式："Previously set the maximum number of characters of a background task's output that the `TaskOutput` tool kept. Claude reads a background task's output file with `Read` instead"）
- url: https://code.claude.com/docs/en/env-vars
- source_type: primary
- published: unknown
- confidence: high

### [13] Token 计数没有免费的精确解：Anthropic 官方 count_tokens 端点免费、独立限速（5k–20k RPM），但文档明示"token count is an estimate... might differ by a small amount"；Claude 4.7+ 换用新 tokenizer 使同文本约多 30% tokens、官方要求"针对目标模型重新计数"——Zen 需要混合计数（本地 tokenizer 估算 + 每轮用响应 usage 的 prompt_tokens 校准 + 安全余量）
- quote: "The token count is an **estimate**. In some cases, the actual number of input tokens used when creating a message might differ by a small amount." / "Recount prompts against the model you plan to use rather than reusing counts measured against earlier models."
- url: https://platform.claude.com/docs/en/build-with-claude/token-counting
- source_type: primary
- published: unknown
- confidence: high

### [14] 社区对自动压缩的信任流失是真实失败模式：有长期用户明确关闭 auto-compact、改为在告警时手动 /compact 或 /clear（"The larger the context gets, the dumber the responses"）；有用户"dreads the dreaded auto compact moment"、靠外部记忆文件补漏； Emacs 自研 harness 的作者指出 Claude 的压缩"invalidates a lot of cached context"，想要更 cache-friendly 的策略；也有用户建议在缓存过期前主动触发压缩作为恢复选项
- quote: "I've disabled \"auto-compact\" in claude code and when I see a warning that it's getting too big, I cut things off, maybe ask the agent to commit, or write a summary, and then /compact or /clear."
- url: https://news.ycombinator.com/item?id=46598495 （缓存批评见 https://news.ycombinator.com/item?id=48883799 ，2026-07-12）
- source_type: community
- published: 2026-01-13
- confidence: high
