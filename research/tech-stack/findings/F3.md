# F3: Agent runtime and MCP

## Findings

### [1] Vercel AI SDK is at v7 (2026) and provides a unified multi-provider TypeScript API covering generateText/streamText, tool calling, streaming, MCP client, agent loop (ToolLoopAgent), and a harness abstraction (HarnessAgent) for Claude Code / Codex / Pi.
- quote: "The AI SDK is the TypeScript toolkit designed to help developers build AI-powered applications and agents with React, Next.js, Vue, Svelte, Node.js, and more."
- url: https://ai-sdk.dev/docs/introduction
- source_type: primary
- published: unknown (current docs, site footer © 2026)
- confidence: high

### [2] AI SDK v7 tool calling uses Zod/JSON Schema inputSchema, optional execute, strict mode, multi-step via stopWhen (default isStepCount(20)), and a prepareStep callback for per-step model/message/tool overrides and context compaction.
- quote: "With the `stopWhen` setting, you can enable multi-step calls in `generateText` and `streamText`. When `stopWhen` is set and the model generates a tool call, the AI SDK will trigger a new generation passing in the tool result until there are no further tool calls or the stopping condition is met."
- url: https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [3] AI SDK toolApproval is the first-class permission/confirmation mechanism: statuses are 'not-applicable' | 'approved' | 'denied' | 'user-approval'; manual approval is a two-call flow (tool-approval-request → tool-approval-response) and the older needsApproval property is deprecated.
- quote: "When a tool requires manual approval, `generateText` and `streamText` don't pause execution. Instead, they complete and return `tool-approval-request` parts in the result content. This means the manual approval flow requires two calls to the model."
- url: https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [4] AI SDK can HMAC-sign tool approvals with experimental_toolApprovalSecret so client-forged approval responses cannot bypass the human-in-the-loop step when server rebuilds conversation from client-sent messages.
- quote: "When you provide a secret, the server HMAC-signs each approval request at issuance and verifies the signature when the approval is replayed. A forged or tampered approval is rejected before the tool executes."
- url: https://ai-sdk.dev/docs/agents/tool-approvals
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [5] @modelcontextprotocol/typescript-sdk v2 is the stable release line, split into @modelcontextprotocol/server and @modelcontextprotocol/client packages, implementing the 2026-07-28 MCP spec; v1.x continues bug/security fixes for at least 6 months after v2 release.
- quote: "This is the `main` branch — v2 of the SDK (`@modelcontextprotocol/server`, `@modelcontextprotocol/client`), implementing the 2026-07-28 MCP spec."
- url: https://github.com/modelcontextprotocol/typescript-sdk
- source_type: primary
- published: unknown (current main branch README)
- confidence: high

### [6] MCP 2026-07-28 spec defines exactly two standard transports: stdio (newline-delimited JSON-RPC over client-launched subprocess standard streams) and Streamable HTTP (HTTP POST to a single endpoint, reply as JSON or request-scoped SSE); custom transports are allowed if they preserve JSON-RPC framing.
- quote: "stdio: newline-delimited messages over the standard streams of a client-launched subprocess. Streamable HTTP: each message is an HTTP POST to a single MCP endpoint; replies arrive as a JSON object or a request-scoped SSE stream."
- url: https://modelcontextprotocol.io/docs/concepts/transports
- source_type: primary
- published: 2026-07-28 (spec version)
- confidence: high

### [7] MCP 2026-07-28 is a stateless protocol: all protocol metadata (protocolVersion, clientInfo, clientCapabilities) travels per-request in _meta fields; servers must not rely on connection/session state, and stdio process lifetime is not a conversation boundary.
- quote: "The Model Context Protocol (MCP) is a **stateless protocol**: all the information needed to process a request is contained in the request itself. A server processes each request independently; no state should be inferred from previous requests."
- url: https://modelcontextprotocol.io/specification/2026-07-28/basic/index
- source_type: primary
- published: 2026-07-28
- confidence: high

### [8] AI SDK's @ai-sdk/mcp createMCPClient supports HTTP (recommended for production), SSE, stdio (local only), and custom transports; it can interop with the official @modelcontextprotocol SDK's StdioClientTransport and StreamableHTTPClientTransport, and supports both legacy initialize handshake and stateless 2026-07-28 via server/discover probe.
- quote: "We recommend using HTTP transport (like `StreamableHTTPClientTransport`) for production deployments. The stdio transport should only be used for connecting to local servers as it cannot be deployed to production environments."
- url: https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [9] MCP tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) are untrusted server-provided hints; AI SDK does not auto-convert them to approval policy and recommends combining them with allowlists, scoped credentials, and explicit toolApproval rules.
- quote: "Annotations are untrusted, server-provided hints. The MCP client does not turn them into an approval policy automatically. Applications should combine them with deterministic controls such as tool allowlists, scoped credentials, and their own `toolApproval` policy."
- url: https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [10] AI SDK provides fingerprintTools + detectToolDrift to detect MCP "rug pull" attacks (server later returns a mutated tool description/schema for the same tool name); the app owns baseline storage and the response to drift (block, force re-approval, or alert).
- quote: "The AI SDK provides two functions to pin the approved definitions and detect changes. `fingerprintTools` digests the server-controlled, security-relevant fields of each tool (string `description`, resolved input schema, and `title`) into a stable map of tool name to digest. `detectToolDrift` diffs two such maps."
- url: https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [11] AI SDK ToolLoopAgent is the recommended agent runtime class: it manages the LLM-tools loop, context, and stopping conditions; HarnessAgent is a separate abstraction for running preconfigured established harnesses (Claude Code, Codex, Pi) with compatible stream/UI primitives.
- quote: "The ToolLoopAgent is the recommended approach for building agents with the AI SDK because it reduces boilerplate, improves reusability, simplifies maintenance."
- url: https://ai-sdk.dev/docs/agents/overview
- source_type: primary
- published: unknown (current docs)
- confidence: high

### [12] MCP servers can send elicitation requests to the client during tool execution (e.g. for user input or confirmation); AI SDK surfaces these via onElicitationRequest and the app must handle accept/decline/cancel actions.
- quote: "Elicitation is a mechanism where MCP servers can request additional information from the client during tool execution. For example, a server might need user input to complete a registration form or confirmation for a sensitive operation."
- url: https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools
- source_type: primary
- published: unknown (current docs)
- confidence: high
