# F4: Browser, Git, GitHub auth

## Findings

### [1] Electron's BrowserView is deprecated; WebContentsView (extends View, exposes `.webContents`) is the supported in-app web panel for Electron desktop agents.
- quote: "BrowserView ... Deprecated" / "A View that displays a WebContents. ... `view.webContents` *Readonly* — A `WebContents` property containing a reference to the displayed `WebContents`. Use this to interact with the `WebContents`, for instance to load a URL."
- url: https://www.electronjs.org/docs/latest/api/web-contents-view
- source_type: primary
- published: unknown (latest docs as of 2026-09)
- confidence: high

### [2] Built-in agent browser understanding can use WebContents.executeJavaScript / executeJavaScriptInIsolatedWorld / capturePage plus the Debugger class (Chrome DevTools Protocol) without spawning a second browser process.
- quote: "const win = new BrowserWindow() win.webContents.executeJavaScript('fetch(...).then(resp => resp.json())', true)" / "Works like `executeJavaScript` but evaluates `scripts` in an isolated context." / "A [`Debugger`](/docs/latest/api/debugger) instance for this webContents." / "An alternate transport for Chrome's remote debugging protocol. ... win.webContents.debugger.attach('1.1') ... win.webContents.debugger.sendCommand('Network.enable')"
- url: https://www.electronjs.org/docs/latest/api/web-contents (also https://www.electronjs.org/docs/latest/api/debugger)
- source_type: primary
- published: unknown (latest docs as of 2026-09)
- confidence: high

### [3] Playwright's Electron API (`_electron`) is explicitly experimental and is for launching/automating Electron apps (tests), not for embedding a product browser; supported Electron versions listed as v12.2.0+, v13.4.0+, v14+.
- quote: "Playwright has **experimental** support for Electron automation. You can access electron namespace via: `const { _electron } = require('playwright');`" / "Supported Electron versions are: v12.2.0+ / v13.4.0+ / v14+"
- url: https://playwright.dev/docs/api/class-electron
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high

### [4] simple-git is a thin Node wrapper that requires a system `git` binary on PATH (customizable via `.customBinary` / `binary` option) and supports plugins for abort, progress, timeout, and spawn ownership — matching a desktop agent that should reuse the user's real git.
- quote: "A lightweight interface for running `git` commands in any node.js application." / "Requires git to be installed and that it can be called using the command `git`." / options: `binary: 'git'`, plugins: AbortController, Custom Binary, Progress Events, Timeout, Spawned Process Ownership
- url: https://github.com/steveukx/git-js
- source_type: primary
- published: unknown (repo main as of 2026-09)
- confidence: high

### [5] isomorphic-git is pure JavaScript (no native libgit2), designed for browser/isomorphic use with pluggable fs/http; it does not yet support git wire protocol v2, and `git.add` requires explicit filepaths (no `git add -A` equivalent without external globbing).
- quote: "isogit is pure JavaScript. this is no small thing." / "Does it support wire protocol version 2? Not yet" / "you need to tell git you deleted a file. ... if you want to add all existing files ... const paths = await globby(['./**', './**/.*'], { gitignore: true });"
- url: https://isomorphic-git.org/docs/en/faq (also https://isomorphic-git.org/docs/en/quickstart)
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high

### [6] GitHub docs recommend building a GitHub App rather than an OAuth App: GitHub Apps use fine-grained permissions, let the user control repo access, and issue short-lived tokens; both use OAuth 2.0.
- quote: "Consider building a GitHub App instead of an OAuth app. ... GitHub Apps can act on behalf of a user ... use fine-grained permissions, give the user more control over which repositories the app can access, and use short-lived tokens."
- url: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps
- source_type: primary
- published: unknown (docs as of 2026-09; page notes apps created before 2026-08-03 wildcard-callback behavior)
- confidence: high

### [7] For GitHub App desktop auth, GitHub explicitly says desktop applications should use OAuth Device Flow (RFC 8628): POST /login/device/code, 8-char user_code, 900s expiry, default 5s poll interval, no client_secret required for device flow.
- quote: "If your app is headless or does not have access to a browser, you should use the device flow to generate a user access token. For example, CLI tools, simple Raspberry Pis, and desktop applications should use the device flow." / "The device_code is 40 characters ... user_code ... 8 characters with a hyphen" / "expires_in ... default is 900 seconds" / "interval ... default is 5 seconds" / "For the device flow, you must pass your app's client ID ... The `client_secret` is not needed for the device flow."
- url: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high

### [8] Desktop apps that do have a browser can use GitHub's web application flow with a loopback redirect (`http://127.0.0.1:port`, not `localhost` per RFC 8252); PKCE (S256) is strongly recommended; code exchange requires client_secret.
- quote: "The optional `redirect_uri` parameter can also be used for loopback URLs, which is useful for native applications running on a desktop computer." / "OAuth RFC recommends not to use `localhost`, but instead to use loopback literal `127.0.0.1` or IPv6 `::1`." / "code_challenge_method ... Must be `S256`" / "client_secret ... Required"
- url: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high

### [9] GitHub App user access tokens (`ghu_`) default to 8h expiry with a 6-month refresh token (`ghr_`); permission is the intersection of app and user fine-grained permissions, and `scope` in the response is always an empty string.
- quote: "By default, the user access token expires after 8 hours. You can use a refresh token to regenerate a user access token." / "access_token ... starts with `ghu_`" / "expires_in ... always be `28800` (8 hours)" / "refresh_token ... starts with `ghr_`" / "refresh_token_expires_in ... always be `15897600` (6 months)" / "scope ... This value will always be an empty string."
- url: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high

### [10] Octokit (`octokit` package) is the batteries-included GitHub SDK for Node/browser/Deno: REST + GraphQL + auth strategies + App/OAuth clients; it implements device-flow via `app.oauth.createToken({ onVerification })`, ships throttle/retry, and requires Node 18+ for native fetch.
- quote: "The all-batteries-included GitHub SDK for Browsers, Node.js, and Deno." / "Example: create a token using the device flow. const { token } = await app.oauth.createToken({ async onVerification(verification) { ... } });" / "Octokit requires Node 18 or higher, which includes a native fetch API."
- url: https://github.com/octokit/octokit.js
- source_type: primary
- published: unknown (repo main as of 2026-09)
- confidence: high

### [11] Electron `safeStorage` is the recommended OS-backed secret store for desktop tokens; Electron now prefers the async API (`encryptStringAsync`/`decryptStringAsync`) over sync, which "may be deprecated in a future version"; Linux without a secret store falls back to `basic_text` (hardcoded plaintext password) and must be detected via `getSelectedStorageBackend()`.
- quote: "We recommend using the asynchronous API (`encryptStringAsync`/`decryptStringAsync`) over the synchronous API. The async API is non-blocking, supports key rotation, and handles temporary unavailability gracefully. The synchronous API may be deprecated in a future version of Electron." / "If no secret store is available, items stored in using the `safeStorage` API will be unprotected as they are encrypted via hardcoded plaintext password. You can detect when this happens when `safeStorage.getSelectedStorageBackend()` returns `basic_text`."
- url: https://www.electronjs.org/docs/latest/api/safe-storage
- source_type: primary
- published: unknown (latest docs as of 2026-09)
- confidence: high

### [12] `keytar` (atom/node-keytar) was archived on 2022-12-15 and is read-only; it was the native Keychain/Secret Service/Credential Vault bridge — new Electron apps should prefer built-in `safeStorage` rather than depending on archived native keytar.
- quote: "This repository was archived by the owner on Dec 15, 2022. It is now read-only." / "A native Node module to get, add, replace, and delete passwords in system's keychain. On macOS the passwords are managed by the Keychain, on Linux they are managed by the Secret Service API/libsecret, and on Windows they are managed by Credential Vault."
- url: https://github.com/atom/node-keytar
- source_type: primary
- published: 2022-12-15 (archive date)
- confidence: high

### [13] Playwright Electron automation also documents that native Electron dialogs cannot be intercepted by Playwright (they go straight to OS APIs from main) and must be stubbed via `electronApplication.evaluate` — a constraint if Zen ever drives its own Electron app with Playwright for tests.
- quote: "Playwright does not intercept the native Electron dialog API (`dialog.showOpenDialog`, `dialog.showSaveDialog`, `dialog.showMessageBox`, etc.) because those calls happen in the Electron main process and go straight to OS APIs."
- url: https://playwright.dev/docs/api/class-electron
- source_type: primary
- published: unknown (docs as of 2026-09)
- confidence: high
